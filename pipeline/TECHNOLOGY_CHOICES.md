# 기술 선택과 대안

이 시스템은 국회 회의록을 주기적으로 수집·가공하고, 대량의 발언을 검색하는 서비스다.
따라서 실시간 트랜잭션 처리보다 **대용량 분석, 원문 보존, 배치 자동화, 검색 품질**을 우선했다.

| 영역 | 선택한 서비스 | 선택 이유 | 주요 대안 |
|---|---|---|---|
| 데이터베이스 | **BigQuery** | 회의록·발언처럼 계속 누적되는 대량 데이터를 SQL로 분석하기 쉽고, 서버 운영 없이 필요한 만큼 확장할 수 있다. Vertex AI Search 입력 테이블도 같은 저장소에서 만들 수 있다. | **Cloud SQL(PostgreSQL)**은 잦은 단건 수정과 트랜잭션이 많은 서비스에 적합하지만, 대규모 전문 조회와 배치 분석은 운영·튜닝 부담이 커진다. |
| 원본 저장소 | **Cloud Storage(GCS)** | 공식 PDF를 저렴하고 내구성 있게 원본 그대로 보존하며, 필요할 때 재처리할 수 있다. DB에 PDF 바이너리를 넣지 않아 비용과 관리 부담도 줄인다. | 로컬 디스크나 DB 저장은 구성이 단순하지만, 확장·백업·재처리 안정성이 떨어진다. |
| 배치 실행 | **Cloud Run Jobs** | 컨테이너 단위로 수집부터 PDF 처리까지 실행하고, 작업이 없을 때 서버 비용이 발생하지 않는다. 기존 Python 코드를 큰 변경 없이 배포할 수 있다. | **Cloud Functions**는 짧고 단순한 작업에 유리하고, **GKE/VM**은 제어 범위가 넓지만 현재 규모에는 운영 부담이 크다. |
| 정기 실행 | **Cloud Scheduler (운영 예정)** | 하루 1회 같은 정해진 주기로 Cloud Run Job을 호출하는 데 충분하며 설정과 비용이 작다. | 복잡한 작업 의존성과 다단계 재시도가 필요해지면 **Cloud Composer(Airflow)**가 더 적합하다. |
| 검색 | **Vertex AI Search** | 키워드 일치뿐 아니라 문맥 기반 검색을 제공하며, 검색 인프라와 모델을 직접 운영하지 않아도 된다. BigQuery의 신규 문서만 증분 반영할 수 있다. | **Elasticsearch/OpenSearch**는 검색 규칙을 세밀하게 제어할 수 있지만 클러스터 운영이 필요하다. 직접 임베딩·벡터 DB를 구축하면 자유도는 높지만 개발과 품질 관리 부담이 커진다. |
| 비밀정보 | **Secret Manager (운영 연결 예정)** | 국회 API 키를 코드나 이미지에 포함하지 않고 서비스 계정 권한으로 안전하게 주입·교체할 수 있다. | 일반 환경변수나 설정 파일은 간단하지만 키 노출과 교체 이력 관리에 취약하다. |

## 결론

현재 구성은 데이터 규모가 커져도 별도 서버 운영을 최소화하면서, 원문부터 검색 문서까지
GCP 안에서 연결할 수 있다는 점이 핵심이다. 반면 실시간 쓰기 요청이 크게 늘면 BigQuery
앞에 Cloud SQL 같은 운영 DB를 추가하고, 작업 흐름이 복잡해지면 Scheduler를 Composer로
교체하는 방안을 검토할 수 있다.
